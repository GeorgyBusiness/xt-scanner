# 05_FILE_STRUCTURE.md (Топология репозитория)

## 1. Эволюционный подход (Disclaimer)
Данная структура является **ориентировочной (базовой)** для старта Итерации 1. В процессе написания кода ИИ-ассистент имеет право адаптировать её (объединять логику в меньшее количество файлов или, наоборот, выделять утилиты), если это диктуется здравым смыслом и упрощает кодовую базу. 
Главное требование — **неукоснительно соблюдать правила импортов (маршрутизацию)**.

## 2. Общая топология (Feature-First Lite)
Проект использует упрощенную версию модульного монолита. Вместо глубокой вложенности папок, фичи представлены едиными файлами (модулями), пока их размер не потребует декомпозиции.

```text
xt-scanner/
├── Code/                       # ИСХОДНЫЙ КОД ПРОЕКТА
│   ├── logs/                   # АВТОГЕНЕРИРУЕМЫЕ ЛОГИ
│   │   ├── signals_log.jsonl   # История арбитражных сигналов (JSON Lines)
│   │   └── signals/            # [Black Box] Детальные JSON отчеты по попыткакам сделок
│   ├── Sounds/                 # Аудиофайлы (mp3) для успешных сделок
│   ├── src/
│   │   ├── core/               # ОБЩИЕ ИНСТРУМЕНТЫ
│   │   │   ├── cdp_client.ts   # Обертка для подключения к Chrome
│   │   │   └── event_bus.ts    # Реализация шины событий
│   │   │
│   │   ├── shared/             # ПЕРЕИСПОЛЬЗУЕМЫЙ КОД
│   │   │   └── types.ts        # DTO интерфейсы (ISignalPayload)
│   │   │
│   │   ├── features/           # БИЗНЕС-ЛОГИКА (Изолированные модули)
│   │   │   ├── scanner.ts      # Анализ трафика, Blacklist, фильтры
│   │   │   ├── browser_tabs.ts # Обработчик: трансформация URL и запрос на открытие вкладок
│   │   │   ├── logger.ts       # Обработчик: запись в файл signals_log.jsonl
│   │   │   ├── xt_orderbook.ts # Модуль поддержания состояния стакана и расчета проскальзывания
│   │   │   ├── xt_sniper.ts    # Модуль эмуляции инъекции кликов и текстового ввода (CDP)
│   │   │   └── trade_executor.ts # Оркестратор Trade Pipeline (связывает Orderbook и Sniper)
│   │   │
│   │   ├── main.ts             # Точка входа: сборка зависимостей, оркестрация CDP-команд
│   │   ├── simulator.ts        # CLI-Симулятор для ручного тестирования сигналов из логов
│   │   ├── test_orderbook.ts   # Изолированный CLI-дашборд визуального тестирования стакана
│   │   ├── test_sniper.ts      # Скрипт визуального тестирования Снайпера (automation)
│   │   └── test_pipeline.ts    # E2E скрипт эмуляции полного цикла сделки
│   │
│   ├── config.ts               # Глобальные настройки (порт, URL-шаблоны)
│   ├── blacklist.txt           # Динамически загружаемый список игнорируемых монет
│   ├── package.json            # Зависимости
│   └── tsconfig.json           # Конфигурация TypeScript
│
└── _docs/                      # ДОКУМЕНТАЦИЯ ПРОЕКТА
```

## 3. Архитектурные границы и правила импортов

Даже в упрощенной структуре соблюдаются следующие архитектурные ограничения:

*   **`features/*` (Бизнес-модули):**
    *   **Запрещено:** импортировать друг друга (например, `browser_tabs.ts` не может импортировать ничего из `scanner.ts`).
    *   **Взаимодействие:** общаются только через события в `core/event_bus.ts`.

*   **`shared/` (Переиспользуемый код):**
    *   Самый нижний слой логики. **НЕ МОЖЕТ** импортировать ничего из `features/` или `core/`.

*   **`main.ts` (Точка входа):**
    *   Выступает как DI Container (Dependency Injection). Здесь импортируется всё, инициализируется ядро и связываются фичи через Event Bus.
