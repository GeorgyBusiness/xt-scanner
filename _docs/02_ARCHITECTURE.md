# 02_ARCHITECTURE.md (Архитектурные паттерны)

## 1. Глобальные паттерны
Проект построен по методологии **Feature-First** (Модульный монолит). 
Основная парадигма взаимодействия компонентов — **Event-Driven Architecture (Событийно-ориентированная архитектура)**. Фичи полностью изолированы друг от друга и общаются исключительно через общую шину событий (Event Bus).

## 2. Технологический стек
* **Runtime:** Node.js.
* **Язык:** TypeScript (строгая типизация всех контрактов и JSON-ответов).
* **Взаимодействие с браузером:** Библиотека `chrome-remote-interface` (нативный CDP-клиент, `puppeteer-core` признан избыточным).

## 3. Слой общих инструментов (Core)
Слой содержит инструменты, которые используют все фичи, но сами фичами не являются:
* **`core/cdp_client.ts`**: Менеджер подключения к Chrome DevTools Protocol. Реализует механизм **Target Discovery** (поиск вкладки сканера среди открытых вкладок). Сначала он запрашивает список вкладок (`CDP.List`), находит нужную по совпадению с `config.SCANNER_URL_MATCH`, и только потом подключается непосредственно к ней. Отвечает за поддержание сессии (Auto-reconnect).
* **`core/event_bus.ts`**: Строго типизированная обертка над нативным `EventEmitter`. Служит единственной шиной обмена сообщениями между фичами, гарантируя слабую связанность (Loose Coupling).

## 4. Слой переиспользуемого кода (Shared)
* **`shared/api/types.ts`**: Центральное хранилище TypeScript-интерфейсов для парсинга WebSocket-сообщений. Здесь жестко задана структура сигнала (поля `arb_percent`, `symbol`, `buy_url` и т.д.), чтобы избежать ошибок Runtime.

## 5. Слой бизнес-логики (Features)
Приложение разделено на независимые фичи, каждая из которых решает только одну задачу:
* **`features/scanner.ts`**: Слушает CDP-трафик (Network domain), выхватывает фреймы веб-сокетов, парсит JSON и фильтрует по целевой CEX. Имеет встроенный In-memory TTL кэш (с фоновой очисткой для предотвращения утечек памяти) для отсечения дублей-спама. 
* **`features/xt_orderbook.ts`**: Независимый модуль для перехвата и ведения живого стакана (In-Memory Orderbook). Слушает `Network.responseReceived` + `Network.getResponseBody` для получения HTTP-слепков, и дельты из `Network.webSocketFrameReceived`. Математически рассчитывает проскальзывание перед входом в сделку.
* **`features/xt_sniper.ts`**: Модуль-исполнитель (Execution). Выступает "руками" системы, осуществляя эмуляцию человека через CDP-команды ввода. Для обхода динамически сгенерированных React-классов использует `Runtime.evaluate` с поиском координат элементов через XPath по статичным лейблам.
* **`features/browser_tabs.ts`**: Выступает слушателем-трансформатором. Подписан на `SignalDetectedEvent`, трансформирует Swap-ссылки Jupiter в Token-ссылки и публикует `OpenBrowserTabsRequest`.
* **`features/logger.ts`**: Подписан на `SignalDetectedEvent`. Синхронно гарантирует наличие папки `logs/` при инициализации и безопасно пишет уникальные сигналы в файл `logs/signals_log.jsonl` в режиме append-only. 

## 5.1 Точка входа и Оркестрация (main.ts / simulator.ts)
* **`main.ts`**: Точка входа в систему (Оркестратор). Подписывается на `OpenBrowserTabsRequest` и через CDP (`Target.createTarget`) открывает сформированные вкладки из `browser_tabs.ts`. Служит DI-контейнером для связывания EventBus и CDP клиента.
* **`simulator.ts`**: Интерактивный симулятор для тестирования. Построчно читает логи (`.jsonl`) и эмулирует получение сигнала (по нажатию Enter), публикуя его в EventBus как если бы это был `scanner.ts`. Используется для отладки открытия вкладок без ожидания реальных сигналов.

## 6. Жизненный цикл обработки сигнала
1. `cdp_client` получает пакет `Network.webSocketFrameReceived` в основном процессе (`main.ts`).
2. Сырые данные отправляются в `scanner.ts`, где фильтруется мусорный трафик, извлекается нужный JSON и применяется TTL кэш.
3. Уникальные чистые сигналы возвращаются в `main.ts`, который публикует их как `SignalDetectedEvent` в общую шину `EventBus`.
4. Параллельно и независимо срабатывают обработчики-подписчики:
   - `logger.ts` сохраняет JSONL-строку в лог-файл.

## 7. Обработка ошибок (Error Handling)
* **Потеря CDP-соединения:** Система ловит ошибку дисконнекта, не завершает процесс (process.exit), а переходит в цикл `while(true)` с попыткой автоматического переподключения (Auto-reconnect).
* **Невалидный JSON и Duck Typing:** Ошибки парсинга логируются без падения системы (Graceful Degradation). Для извлечения данных используется утиная типизация (Duck Typing) внутри интерфейсов. Жесткая runtime-валидация через сторонние библиотеки (например, Zod) намеренно не применяется, чтобы снизить хрупкость системы и обеспечить обработку всех подходящих объектов в массиве, даже если структура соседних отличается.
