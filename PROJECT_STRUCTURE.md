import CDP from 'chrome-remote-interface';
import { config } from '../../config';

export async function connectCDP() {
    try {
        const client = await CDP({
            host: config.CDP_HOST,
            port: config.CDP_PORT,
        });

        console.log(`[CDP Client] Connected to Chrome at ${config.CDP_HOST}:${config.CDP_PORT}`);

        client.on('disconnect', () => {
            console.error('[CDP Client] Disconnected from Chrome. Exiting...');
            process.exit(1);
        });

        return client;
    } catch (err) {
        console.error(`[CDP Client] Failed to connect to Chrome at ${config.CDP_HOST}:${config.CDP_PORT}.`, err);
        process.exit(1);
        throw err;
    }
}

```

#### 📄 Code/src/main.ts

import { connectCDP } from './core/cdp_client';

async function main() {
    console.log('[Main] Starting XT Scanner Iteration 1...');

    const client = await connectCDP();
    const { Network } = client;

    try {
        await Network.enable();
        console.log('[Main] Network domain enabled. Listening for WebSocket frames...');

        Network.webSocketFrameReceived((params: any) => {
            console.log('[WebSocket Frame Received]:', JSON.stringify(params, null, 2));
        });

        // Keep process alive
        process.on('SIGINT', async () => {
            console.log('\n[Main] Closing CDP connection...');
            await client.close();
            process.exit(0);
        });
    } catch (err) {
        console.error('[Main] Error during CDP operations:', err);
        await client.close();
        process.exit(1);
    }
}

main();

# 01_BUSINESS_DOMAIN.md (Смыслы и Правила)

## 1. Суть продукта
**XT Scanner** — это локальная автоматизированная система для эксплуатации арбитражных возможностей (latency arbitrage) в направлении XT.com -> DEX (покупка на отстающей CEX XT.com и продажа на ценообразующей DEX, такой как Jupiter). Система работает не как самостоятельный сканер, а как скрытый наблюдатель, пассивно подключаясь к сетевому трафику стороннего веб-сканера сигналов в браузере пользователя.

## 2. Бизнес-логика и Механика
* **Источник данных:** WebSocket-трафик оригинального веб-сканера. Перехват осуществляется через Chrome DevTools Protocol (CDP).
* **Триггер:** Поступление JSON-сообщения, содержащего связку XT.com -> DEX. Сигнал отлавливается на уровне сетевого слоя браузера.
* **Целевое действие:** Мгновенное автоматическое открытие двух вкладок:
  1. График монеты на Jupiter (секундный таймфрейм).
  2. Страница торгов монетой на XT.com для ручного совершения сделки.
* **Логирование:**
  * **Итерация 1 (Текущая):** Сохранение всех поступающих сигналов локально в файл `signals_log.json` (или `.txt`/`.md`) в директории проекта для последующего ретроспективного анализа.
  * **Итерация 2 (Будущая):** Интеграция системных уведомлений ОС (OS Notifications) для быстрого визуального контроля без переключения окон.
* **Правила безопасности (Anti-Ban):**
  * **Строгий Read-Only режим:** Абсолютно ЗАПРЕЩАЕТСЯ вмешиваться в DOM-дерево страницы стороннего сканера, использовать команды `Runtime.evaluate` для инъекции JS-кода или изменять глобальные переменные.
  * Запрещается создавать параллельные WebSocket подключения к серверу сканера.
  * Телеметрия стороннего сканера (`ui_telemetry_batch`) не должна блокироваться; система должна позволять браузеру естественным образом отправлять данные о потере фокуса при открытии новых вкладок.
  * CDP-подключение должно производиться на нестандартный порт (отличный от дефолтного 9222).

## 3. Сущности
* **Target CEX:** Целевая биржа для покупки на отставании (XT.com).
* **Reference DEX:** Ценообразующая биржа, куда планируется вывод (Jupiter, Raydium).
* **CDP Listener:** Локальный скрипт-перехватчик трафика, слушающий порт отладки браузера.

## 4. Формирование URL
* **XT.com:** `https://www.xt.com/en/trade/{symbol}_usdt`
* **Jupiter:** `https://jup.ag/tokens/{address}`

# 02_ARCHITECTURE.md (Архитектурные паттерны)

## 1. Глобальные паттерны
Проект построен по методологии **Feature-First** (Модульный монолит). 
Основная парадигма взаимодействия компонентов — **Event-Driven Architecture (Событийно-ориентированная архитектура)**. Фичи полностью изолированы друг от друга и общаются исключительно через общую шину событий (Event Bus).

## 2. Технологический стек
* **Runtime:** Node.js.
* **Язык:** TypeScript (строгая типизация всех контрактов и JSON-ответов).
* **Взаимодействие с браузером:** Библиотека `chrome-remote-interface` (нативный CDP-клиент, `puppeteer-core` признан избыточным).

## 3. Слой общих инструментов (Core)
Слой содержит инструменты, которые используют все фичи, но сами фичами не являются:
* **`core/network/cdp_client.ts`**: Менеджер подключения к Chrome DevTools Protocol. Отвечает за установку соединения на нестандартном порту и поддержание сессии.
* **`core/event_bus/`**: Реализация шины событий. Центр обмена сообщениями между фичами.

## 4. Слой переиспользуемого кода (Shared)
* **`shared/api/types.ts`**: Центральное хранилище TypeScript-интерфейсов для парсинга WebSocket-сообщений. Здесь жестко задана структура сигнала (поля `arb_percent`, `symbol`, `buy_url` и т.д.), чтобы избежать ошибок Runtime.

## 5. Слой бизнес-логики (Features)
Приложение разделено на независимые фичи, каждая из которых решает только одну задачу:
* **`features/signal_interceptor`**: Слушает CDP-трафик (Network domain), выхватывает фреймы веб-сокетов, парсит JSON, проверяет соответствие паттерну (XT -> DEX) и публикует событие `SignalDetectedEvent` в Event Bus.
* **`features/tab_manager`**: Подписан на `SignalDetectedEvent`. При получении события формирует целевые URL (Jupiter и XT.com) и отправляет команду в CDP на открытие двух новых вкладок (Target.createTarget).
* **`features/logger`**: Подписан на `SignalDetectedEvent`. Отвечает за форматирование данных и их безопасную запись в локальный файл `signals_log.json`. В Итерации 2 сюда будет добавлена логика системных уведомлений (OS Notifications).

## 6. Жизненный цикл обработки сигнала
1. `cdp_client` получает пакет `Network.webSocketFrameReceived`.
2. `signal_interceptor` фильтрует мусорный трафик и телеметрию, извлекая нужный JSON.
3. `signal_interceptor` публикует `SignalDetectedEvent` в `EventBus`.
4. Параллельно и независимо срабатывают обработчики:
   - `tab_manager` открывает вкладки через CDP.
   - `logger` сохраняет JSON на диск.

## 7. Обработка ошибок (Error Handling)
* **Потеря CDP-соединения:** Система должна автоматически пытаться переподключиться к браузеру с экспоненциальной задержкой (Exponential Backoff).
* **Невалидный JSON:** Ошибки парсинга (например, изменение структуры сигнала разработчиками сканера) логируются локально, система не падает (Graceful Degradation).
```

# 03_DATA_AND_STATE.md (Данные и Состояние)

## 1. Схема хранения данных (Data Persistence)
Система работает без тяжелых баз данных. Используется максимально простое локальное хранилище.
* **Файл логов:** `signals_log.jsonl` (JSON Lines — каждая новая строка это отдельный валидный JSON объект). Расположен в корне проекта.
* **Механика:** Режим `append-only`. Скрипт только дописывает новые строки в конец файла. Это работает мгновенно и безопасно для файловой системы.

## 2. Управление состоянием (State Management)
Глобальное состояние живет в оперативной памяти (RAM) процесса Node.js.

### 2.1. Состояние CDP-подключения
* Хранит ссылку на активную сессию браузера (`CDP Session`).
* Статусы: `DISCONNECTED`, `CONNECTED`. На этапе Итерации 1 при обрыве связи скрипт завершает процесс (Fail-Fast).

### 2.2. Анти-спам кэш (Tab Manager State)
* **Проблема:** Защита браузера от зависания при спаме однотипными сигналами.
* **Хранилище:** In-memory `Set<string>` или `Map<string, number>`.
* **Ключ:** `symbol` (например, `PYBOBO`).
* **Логика (TTL):** После успешного открытия вкладок тикер заносится в кэш на 60 секунд. Все последующие сигналы с этим тикером в течение минуты логируются в файл, но **не открывают** новые вкладки.

## 3. Контракты данных (TypeScript DTOs)
Строгая типизация входящего сигнала из WebSocket-трафика. 

```typescript
// shared/api/types.ts

export interface ISignalPayload {
  symbol: string;             // Тикер (например, "PYBOBO")
  address: string;            // Смарт-контракт для ссылки на Jupiter
  network: string;
  arb_percent: number;        // % профита
  arbitrage_amount_usdt: number; // Объем профита в USDT
  
  // Данные бирж
  big: IExchangeData;         // Должно содержать XT.com (CEX)
  small: IExchangeData;       // Должно содержать Jupiter/Raydium (DEX)
}

  exchange: string;           // Фильтруем по этому полю (ищем 'xt', 'xtcom' и т.д.)
  market: string;
  symbol: string;
}
```

## 4. Правила доступа к данным
Модуль фильтрации (в слое features/) сначала проверяет наличие тикера в In-memory кэше, и только если его там нет — публикует событие на открытие вкладок через Event Bus.

```

# 04_INTEGRATIONS.md (Внешние сервисы и Сеть)

## 1. Интеграция с локальным браузером (CDP)
Главная интеграция системы — подключение к уже запущенному экземпляру Google Chrome на компьютере пользователя.
* **Протокол:** Chrome DevTools Protocol (CDP).
* **Библиотека:** `chrome-remote-interface` (Node.js).
* **Сетевая инфраструктура:** Подключение происходит исключительно через `localhost` (127.0.0.1) на кастомный порт отладки (например, `48192`), отличный от стандартного 9222.
* **Жизненный цикл (Ручной запуск):** Скрипт работает в режиме "On-Demand" (по запросу). Пользователь вручную запускает скрипт (через терминал или ярлык) после открытия целевой вкладки сканера. Остановка скрипта мгновенно разрывает CDP-сессию без влияния на работу браузера.

## 2. API-провайдеры (Биржи)
В рамках Итерации 1 скрипт **НЕ использует** REST/WebSocket API бирж (XT.com, Jupiter). 
* **Как работает:** Взаимодействие с биржами происходит исключительно через генерацию URL-ссылок и открытие их в браузере (`Target.createTarget` через CDP). Сделки совершаются пользователем вручную.

## 3. Сетевая инфраструктура и Антифрод
* Скрипт является полностью пассивным слушателем (Read-Only) на сетевом слое (Network Domain CDP).
* Телеметрия стороннего сканера (`ui_telemetry_batch`) уходит на сервер провайдера в штатном режиме.

## 1. Контекст и Бизнес-задача (Context)
* Для реализации системы "XT Scanner" необходимо научиться подключаться к запущенному экземпляру Google Chrome и пассивно перехватывать сырой сетевой трафик (WebSocket) без вмешательства в работу страниц.
* **Проблема выбора:** Выбор между `puppeteer-core` и `chrome-remote-interface`.
* **Решение:** Проведенный ресерч показал, что `puppeteer-core` имеет жесткую привязку к версиям браузера и избыточен для задач без DOM-манипуляций. Выбрана библиотека `chrome-remote-interface` для обеспечения максимальной совместимости (Forward Compatibility) с будущими версиями Chrome.

## 2. Предлагаемое решение (Proposed Solution)
* Инициализация базового Node.js + TypeScript проекта.
* Использование `chrome-remote-interface` для подключения к Chrome по CDP (Chrome DevTools Protocol).
* Создание глобального конфигурационного файла `config.ts`, в который сразу закладываем параметры для будущих этапов (включая флаг `OPEN_TABS_IN_BACKGROUND`).
* Создание базового модуля `cdp_client.ts` в слое общих инструментов (Core) для инкапсуляции логики подключения.
* На данном этапе (Итерация 1) авто-переподключение (Exponential Backoff) не реализуется. При обрыве связи скрипт должен выводить ошибку в консоль и завершать процесс (Fail-Fast).
* Входная точка `main.ts` должна устанавливать соединение, включать домен `Network` и логировать сырые события `Network.webSocketFrameReceived` прямо в терминал.

## 3. Изменения в Данных и Состоянии (Data & State)
* **БД:** База данных не используется.
* **State:** Состояние подключения (активно/разорвано) хранится в оперативной памяти внутри `cdp_client.ts`.

## 4. Интеграции и AI (Integrations)
* Подключение осуществляется локально (127.0.0.1) на кастомный порт отладки (по умолчанию `48192`). 
* Пользователь должен запускать Chrome со специальным флагом (например, `--remote-debugging-port=48192`).
